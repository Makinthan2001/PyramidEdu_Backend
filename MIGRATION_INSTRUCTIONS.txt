Database migration instructions — PyramidEdu_Backend

Purpose
- Instructions for applying Prisma schema changes (prisma/schema.prisma) to your database and updating the Prisma client.

IMPORTANT SAFETY NOTES
- Never run destructive commands (e.g., `prisma migrate reset`) against production unless you intend to drop and recreate the database.
- Always back up your production database before applying schema changes.
- Ensure the `DATABASE_URL` in your environment refers to the intended database before running migrations.

Local development (recommended flow)
1. Open the backend folder:
   cd "d:\6th Semester\Project 2\PyramidEdu_Backend"

2. Check migration status (shows applied migrations and drift):
   npx prisma migrate status --schema prisma/schema.prisma

3. Create and apply a new migration (development):
   npx prisma migrate dev --name <descriptive_name> --schema prisma/schema.prisma
   Example:
   npx prisma migrate dev --name add_force_password_change --schema prisma/schema.prisma

   - This will:
     * Create a migration file in `prisma/migrations/`
     * Apply it to your development database
     * Regenerate the Prisma Client automatically (or run `npx prisma generate` after)

4. (Optional) If Prisma did not regenerate client automatically, run:
   npx prisma generate --schema prisma/schema.prisma

5. Restart your development server so it uses the updated Prisma Client:
   npm run dev

Production / CI (safe, non-destructive deploy)
1. Build your application using your CI pipeline (typescript compile etc.).
2. In deployment step, apply migrations with `migrate deploy` (this will run SQL migrations without prompting or resetting data):
   npx prisma migrate deploy --schema prisma/schema.prisma
3. Regenerate client if needed (usually part of build step):
   npx prisma generate --schema prisma/schema.prisma
4. Restart the production server.

If Prisma reports "drift detected"
- The migration history in `prisma/migrations` does not match the current DB schema.
- For development you can reset the database to match migrations (this will DROP ALL DATA):
   npx prisma migrate reset --schema prisma/schema.prisma
- For production DO NOT use `migrate reset`. Instead:
  * Inspect differences carefully; consider creating a new migration that brings the DB into sync
  * Take backup and run `migrate deploy` after validating SQL
  * Consult DBA if necessary

Verifying schema changes
- After applying migration, check:
  npx prisma migrate status --schema prisma/schema.prisma
- Inspect database table columns (Postgres example using psql):
  SELECT column_name FROM information_schema.columns WHERE table_name = 'users';
- Query with Prisma to verify fields are accessible in code; restart server first.

Troubleshooting
- "Could not find Prisma Schema" — run commands from the backend workspace root or pass `--schema prisma/schema.prisma` explicitly.
- "Column does not exist" after migration — ensure the server is connected to the same `DATABASE_URL` used when running migrations, and restart the server to pick up the regenerated Prisma client.
- If you used a managed DB provider (Neon, Supabase, etc.), ensure the connection string (and any connection pooling/roles) allow migrations.

Example common commands (copy/paste)
# check status
npx prisma migrate status --schema prisma/schema.prisma

# create and apply migration (development)
npx prisma migrate dev --name add_force_password_change --schema prisma/schema.prisma

# regenerate client
npx prisma generate --schema prisma/schema.prisma

# reset (DESTRUCTIVE — development only)
npx prisma migrate reset --schema prisma/schema.prisma

# deploy migrations (production / CI)
npx prisma migrate deploy --schema prisma/schema.prisma

Remember to restart your Node process after migrations so the new Prisma Client is used.
